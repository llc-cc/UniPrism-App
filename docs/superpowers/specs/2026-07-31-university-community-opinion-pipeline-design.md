# 高校社区评价采集与观点模型设计

## 1. 目标与首期范围

首期以“北京大学”为试点，将公开社区中分散的校园与专业体验，转换为可审核、可追溯、可供 App 检索的结构化观点。

首期只接入：

- 知乎公开页面；
- 百度贴吧公开页面；
- 北京大学；
- 学校、专业、课程、就业、宿舍、食堂、社团七个评价维度。

首期不接入小红书、抖音、快手和 B 站。上述平台需要登录限制、视频语境和独立来源策略验证，待首期质量稳定后逐个平台增加。

## 2. 安全与采集边界

采集 Agent 必须遵守以下边界：

- 仅发现和访问无需登录即可查看的公开页面；
- 不隐藏或轮换 IP，不使用普通账号 Cookie，不绕过验证码、登录、403、robots 或平台访问限制；
- 每个平台使用独立策略配置，明确允许域名、速率、并发数、页面上限和内容保留范围；
- 页面受阻时记录受阻原因并停止该地址，不将其当作空内容继续处理；
- 不长期保存昵称、账号 ID、头像、个人主页、手机号、微信、QQ、二维码等个人信息；
- 原始内容只在采集与脱敏期间短暂存在内存中，数据库保存原始内容哈希、公开来源链接和脱敏后的证据正文；
- 首期所有有效证据均进入人工审核，未审核内容不得参与 App 问答。

## 3. 推荐架构

系统采用“有效证据 + 聚合观点”双层模型，而不是直接保存全部评论或只保存 AI 结论。

```text
关键词规划
  → 公开链接发现
  → 平台策略检查
  → 无头浏览器受控访问
  → 公开正文/评论提取
  → 规则清洗与隐私脱敏
  → 精确去重与语义聚类
  → AI 质量判断和观点提取
  → 人工审核
  → 学校/专业观点聚合
  → 审核通过的聚合结果参与 App 问答
```

### 3.1 链接发现器

链接发现器根据“北京大学 + 评价维度 + 平台限定词”生成查询，例如：

- 北京大学 计算机 课程压力 知乎；
- 北京大学 宿舍 食堂 贴吧；
- 北京大学 社团 校园生活 知乎。

发现器通过可配置的合规搜索服务获得候选公开链接。没有配置搜索服务凭据时，任务状态必须显示“发现服务未配置”，不能伪装成采集成功。

候选链接先经过平台、域名和 URL 规则校验，再进入采集队列。相同链接只保留一个任务。

### 3.2 平台采集适配器

知乎和贴吧各自使用独立适配器，负责：

- 判断页面是否公开可访问；
- 提取帖子标题、正文、公开评论、发布时间和页面上可见的互动数量；
- 识别登录页、验证码、访问限制和页面结构变化；
- 输出统一的候选证据结构。

单个平台解析规则变化时，只修改对应适配器，不影响官方高校页面爬虫和其他平台。

### 3.3 规则清洗器

规则清洗在调用 AI 前完成：

- HTML、按钮、导航、页脚和平台固定文案清理；
- Unicode、空白、标点和异常字符规范化；
- 纯表情、灌水、过短文本和乱码过滤；
- 手机号、微信、QQ、邮箱、账号、个人主页等隐私信息脱敏；
- 广告和引流使用多信号评分，不因单独出现“微信”或“咨询”就直接删除；
- 完全相同内容使用内容哈希去重；
- 高相似内容进入同一语义聚类，保留代表证据和重复数量，不直接丢失群体一致性信息。

清洗结果分为：

- `rejected`：明确垃圾、广告、无意义或隐私风险无法消除；
- `review_required`：内容有价值但存在事实、情绪或隐私不确定性；
- `candidate`：规则检查通过，等待 AI 分析和首期人工审核。

### 3.4 AI 质量与观点分析

AI 只能分析已经脱敏的候选证据，输出固定 JSON 结构：

- 学校；
- 专业（可为空）；
- 评价维度；
- 原子观点；
- 分维度情绪；
- 信息价值；
- 可信度；
- 事实性与主观性标记；
- 风险原因；
- 是否需要人工审核；
- 模型与提示词版本。

AI 不得仅凭“本人是某校学生”的自述判定身份真实。自述身份只能作为弱信号，不保存可识别用户身份的信息。

### 3.5 去重与可信度

去重分两级：

1. 规范化文本哈希处理完全重复；
2. 向量相似度处理改写和近义重复。

语义相似内容聚类后保留：

- 代表证据；
- 聚类样本数量；
- 不同平台数量；
- 最早与最近出现时间；
- 支持和反对样本数量。

可信度由以下因素组成：

- 内容具体程度；
- 信息完整度；
- 多条独立证据的一致性；
- 来源平台多样性；
- 时间新鲜度；
- 有限互动权重；
- 人工审核结果。

互动数量使用封顶或对数权重，避免一条高赞内容压过大量独立样本。最终评价必须同时显示样本数、来源数、更新时间和观点分歧，不只显示一个看似精确的分数。

## 4. 数据模型

### 4.1 复用现有内容表

脱敏后的有效证据继续使用现有内容采集表：

- `content_sources`：知乎、贴吧等来源策略；
- `content_ingestion_batches`：每次发现、采集和处理的批次；
- `content_items`：证据元数据、来源链接、状态和去重标识；
- `content_documents`：脱敏后的证据正文；
- `content_versions`：内容变化与清洗版本；
- `content_rights_snapshots`：来源权限与处理策略快照。

社区证据默认设置为：

- `allowRecommend = false`；
- `allowPush = false`；
- `reviewStatus = pending` 或 `human_required`；
- `lifecycleStatus = review_required`。

审核通过后仍不直接把单条评论原样推给用户，只允许其成为聚合观点的证据。

### 4.2 新增观点分析表

新增 `community_evidence_analyses`，每条证据最多对应一条当前分析结果，保存：

- 内容证据 ID；
- 学校标准编码；
- 专业标准编码（可为空）；
- 维度；
- 原子观点；
- 分维度情绪；
- 信息价值分；
- 可信度分；
- 垃圾与风险原因；
- 重复聚类 ID；
- 分析状态；
- 模型、提示词和规则版本；
- 审核人、审核时间和审核结果。

新增 `community_opinion_aggregates`，保存审核通过证据形成的聚合观点：

- 学校与专业；
- 评价维度；
- 聚合观点；
- 综合分与置信度；
- 支持、反对和总样本数；
- 来源平台数；
- 数据时间范围；
- 最近计算时间；
- 是否允许参与 App 检索。

聚合表不覆盖证据表。每个聚合观点必须能够追溯到支持它的审核通过证据。

## 5. 管理端设计

只扩展现有 `/admin/content-ingestion` 内容采集监控中心，不修改邀请码或其他管理页面。

现有页面增加以下页签：

- 采集总览；
- 数据源；
- 执行记录；
- 内容审核；
- 社区评价；
- 错误日志。

### 5.1 内容审核

列表显示：

- 学校、专业和平台；
- 清洗后的证据正文；
- AI 提取的观点与维度；
- 信息价值、可信度和风险提示；
- 原始公开链接；
- 采集时间；
- 重复聚类与相似样本数；
- 通过、拒绝、修改后通过。

首期不提供批量自动通过。审核动作必须记录管理员、时间、原结果和修改后的结果。

### 5.2 社区评价

北京大学详情显示：

- 发现链接数；
- 成功访问数；
- 受阻数；
- 提取评论数；
- 规则拒绝数；
- 有效证据数；
- AI 已分析数；
- 待审核数；
- 已形成观点数。

评价画像按七个维度显示综合结果、样本数、平台数、更新时间、情绪分布和观点分歧。

## 6. App 使用规则

App 只检索满足以下条件的聚合观点：

- 对应证据已经审核通过；
- 聚合观点允许参与检索；
- 置信度和有效样本数达到配置阈值；
- 数据未过期；
- 用户问题与学校、专业和评价维度匹配。

样本不足时，App 使用正常的用户引导语言，不向用户显示“正在清洗”“没有入库”“同步失败”等后端术语。

回答需要展示来源时，引用聚合观点对应的公开帖子链接，并明确社区观点不代表学校官方结论。

## 7. 调度、开关与监控

社区评价采集使用独立开关和定时计划，不复用高校官方页面总开关，避免关闭社区采集时影响现有学校官网定时任务。

首期默认关闭自动定时，由管理员完成一次手动试跑和审核后再开启。管理端能够：

- 开启或关闭社区评价总开关；
- 手动运行北京大学试点；
- 查看下次计划时间；
- 查看每个平台的成功率和受阻原因；
- 查看清洗、去重、AI、审核和聚合各阶段数量。

## 8. 错误处理

- 搜索服务未配置：任务不启动，显示明确配置状态；
- 平台受阻：记录平台、URL、HTTP 状态和受阻类型，不重试绕过；
- 页面结构变化：标记适配器解析失败并进入错误日志；
- AI 超时或输出不合法：证据保留为待分析，不进入聚合；
- 数据库写入失败：批次标记失败或部分完成，保持幂等重试；
- 同一发现任务和同一证据使用幂等键，重复执行不会重复入库；
- 聚合失败不影响已经审核通过的证据。

## 9. 测试与验收

### 9.1 自动测试

- 链接域名白名单、非法跳转和受阻页面测试；
- 联系方式脱敏、广告、灌水、过短和正常文本边界测试；
- 完全去重与语义聚类测试；
- AI JSON 协议、异常输出和超时测试；
- 证据入库幂等、版本更新和审核状态测试；
- 审核权限与审核审计测试；
- 聚合观点只使用已审核证据测试；
- App 检索不得命中待审核、拒绝或过期内容测试；
- 管理端页面和接口测试。

### 9.2 首期人工验收

北京大学试点需能够直观看到完整链路：

```text
发现链接 → 访问/受阻 → 提取 → 规则过滤 → AI 分析
→ 待审核 → 审核通过 → 形成观点 → App 检索命中
```

平台拒绝访问不视为系统故障，但必须准确显示受阻原因。系统不得为了达到数量目标绕过平台限制。

## 10. 后续阶段

首期质量通过后按以下顺序扩展：

1. 增加更多高校；
2. 接入小红书，重点提取校园生活体验；
3. 接入 B 站、抖音和快手，先处理视频标题、简介和公开文字评论；
4. 扩展社会热点和用户相关内容；
5. 数据量达到关系型数据库检索瓶颈后，再将审核通过的证据和聚合观点同步至 Elasticsearch。

每个平台单独评审来源权限和采集策略，不能因为已有一个平台适配器就默认允许其他平台。
