# B 类体验语料自动分流与规模化采集设计

## 1. 目标与适用范围

本设计调整 UniPrism B 类低频体验语料的入库与审核流程，解决两个问题：

1. 垃圾、重复和低价值内容不应长期占用 MySQL；
2. 数据量扩大后，管理员不能逐条审核全部采集内容。

首轮仍以北京大学为试点，覆盖学校整体、专业、课程、就业、宿舍、食堂、社团与校园文化七个维度。当前可运行平台仍为知乎和贴吧；哔哩哔哩、豆瓣和小红书必须分别完成来源治理与平台适配后再接入，不能因本次分流改造而默认开放。

本设计覆盖旧设计中“首批所有有效证据均进入人工审核”的规则。新的目标是：自动处理绝大多数内容，人工审核只处理冲突、高风险和系统抽检样本。

## 2. 核心原则

- 技术暂存不等于业务入库；只有审核通过的证据可以进入长期证据库。
- 明确垃圾、广告、无关、过短和无法脱敏的内容不保存正文。
- 高质量、安全且来源权限允许的内容可以自动审核通过。
- 负面体验不等于垃圾；具体、可归因的负面经历与正面经历使用相同质量门槛。
- App 只读取已发布聚合，不读取临时文本、待审候选或单条社区评论。
- 数量目标按“有效证据”计算，不按抓取到的原始评论数量计算。

## 3. 处理架构

```text
平台公开页面
  -> 采集 Agent
  -> Redis 临时样本（短期 TTL）
  -> 程序预过滤与精确去重
       -> 明确垃圾：删除正文，仅保留短期去重指纹
       -> 合格候选：进入 AI 分析
  -> AI 质量、可信度、时效与风险分析
       -> 高质量且安全：自动通过，写入 experience_evidence
       -> 低质量或无价值：删除正文，仅保留短期去重指纹
       -> 冲突或高风险：写入 experience_review_candidates
  -> 人工审核少量候选
       -> 通过：写入 experience_evidence
       -> 拒绝：删除候选正文，保留短期去重指纹和审计计数
  -> 生成 experience_signal_aggregates
  -> 聚合审核与发布
  -> App 检索
```

Redis 只承担短期传输和处理状态，不作为长期事实来源。MySQL 只保存有效证据、少量待审候选、聚合结果和必要的批次审计统计。

## 4. 自动分流规则

### 4.1 程序预过滤

调用 AI 前完成以下低成本判断：

- HTML、导航、页脚、平台固定文案和异常字符清理；
- 广告、联系方式、二维码、引流和机器人文本识别；
- 无关学校、实体歧义和维度不匹配过滤；
- 过短、纯表情、灌水、辱骂但不包含有效经历的内容过滤；
- 规范化哈希精确去重；
- 来源 URL、域名、权限和保留策略检查；
- 能够确定处理的隐私字段脱敏。

明确拒绝的正文不写入 MySQL。系统只增加批次拒绝计数，并在 Redis 保存去重指纹，默认 TTL 为 90 天。

### 4.2 AI 自动通过

同时满足以下条件时自动通过：

- 规则质量分不低于 80；
- AI 信息价值不低于 7；
- 可信度不低于 6；
- AI 质量状态为 `usable` 或 `high_value`；
- 不包含隐私、安全或违法风险；
- AI 未要求人工复核；
- 来源状态有效、权限未过期且允许推荐。

自动通过必须记录模型、提示词、规则版本、评分、自动审核人和审核原因。自动通过等同于系统审核通过，但仍需进入随机质量抽检。

### 4.3 自动拒绝

满足任一明确低质条件时自动拒绝：

- 规则清洗器判定为垃圾或不可用；
- 规则质量分低于 50；
- AI 信息价值低于 4；
- AI 状态为 `low_context`；
- 确认重复且已有代表性证据；
- 与学校或任务维度无关。

自动拒绝不创建长期证据记录，也不进入管理员逐条审核列表。批次只保留原因分布和数量统计。

### 4.4 人工审核

只有以下内容进入人工审核：

- 有信息价值但来源或时效不足；
- AI 明确要求人工判断；
- 涉及隐私、安全、违法、严重指控或身份真实性；
- 多个来源对同一事实给出明显冲突结论；
- 自动通过样本的随机抽检，建议为 1%；
- 管理员配置的专项复核任务。

人工审核量目标为全部原始采集内容的 1%–3%。超过 3% 时监控中心必须提示分流规则异常，并按平台、维度和原因展示占比，不能把积压简单交给管理员处理。

## 5. 数据归属与保留策略

### 5.1 Redis 临时数据

Redis 保存：

- 待预过滤的临时正文；
- 待 AI 分析的脱敏正文；
- 自动拒绝与人工拒绝的内容哈希；
- 任务租约、重试和阶段状态。

临时正文建议 TTL 为 24 小时；拒绝指纹建议 TTL 为 90 天。正文处理成功、拒绝或超时终止后应主动删除，不等待 TTL 作为唯一清理方式。

### 5.2 MySQL 长期数据

- `experience_collection_runs`：保存批次、平台、维度、阶段计数和错误原因，不保存垃圾正文。
- `experience_review_candidates`：新增，仅保存少量必须人工判断的脱敏候选。
- `experience_evidence`：调整为只保存自动通过或人工通过的有效证据。
- `experience_signal_aggregates`：保存由有效证据形成的七维聚合画像。
- `experience_aggregate_evidence`：保留聚合与有效证据的可追溯关系。

人工拒绝后，`experience_review_candidates` 中的正文应删除；保留审核人、审核时间、拒绝原因、不可逆内容哈希和来源标识。拒绝内容不能转入 `experience_evidence`。

现有数据迁移必须先备份并输出数量核对报告：已通过证据保留；待审内容迁入候选表；已拒绝正文清理后仅保留最小审计信息。迁移不得静默删除数据。

## 6. 北京大学首轮数量目标

首轮数量使用以下漏斗目标：

- 原始采集：2,000–5,000 条；
- 预过滤和去重后：约 1,000–2,000 条；
- 最低有效证据：500 条；
- 理想有效证据：800 条；
- 人工审核：不超过原始采集量的 3%。

七个维度的理想有效证据配额为：

| 维度 | 目标数量 |
|---|---:|
| 学校整体 | 100 |
| 专业体验 | 250 |
| 课程与学习压力 | 120 |
| 就业与发展 | 120 |
| 宿舍 | 80 |
| 食堂 | 50 |
| 社团与校园文化 | 80 |
| 合计 | 800 |

500 条为首轮可用门槛，800 条为完整目标。达到总量但某个维度明显不足时，任务不能只显示“已完成”，应生成该维度的补采任务。

## 7. 规模化采集策略

单个浏览器任务保持小批次，建议每次提交 30–50 条候选，避免长事务、页面失效和失败后全批重跑。编排器按照“学校 × 平台 × 维度 × 查询词 × 分页游标”拆分任务，并通过幂等键和内容哈希合并结果。

任务停止条件按有效证据配额判断：

1. 维度已达到目标且来源分布满足要求；
2. 可发现页面已经耗尽；
3. 平台出现登录失效、验证码、403 或权限过期；
4. 达到平台请求、页面或时间预算。

不得为了达到 500–800 条目标而绕过平台限制、降低质量阈值或重复保存相似内容。某个平台受阻时应显示真实缺口，由其他已获准来源补充，或等待人工恢复合法访问条件。

## 8. 管理端调整

内容监控中心将数据分为四类，避免把技术暂存误称为正式入库：

- 采集原始量：只显示计数；
- 自动淘汰量：按广告、重复、过短、无关、低信息等原因汇总；
- 有效证据量：自动通过与人工通过的长期证据；
- 待人工审核量：只显示风险、冲突和抽检候选。

审核页面默认按风险和信息价值排序，展示准确的待审原因。页面不再把所有中等分数内容都列为待审。管理员拒绝候选后，页面应明确提示“正文已清理，仅保留审计指纹”。

监控中心还应展示：

- 七维配额进度；
- 平台来源分布；
- 自动通过率、自动拒绝率和人工审核率；
- 人工审核率超过 3% 的告警；
- Redis 临时队列积压和最老任务年龄；
- 自动删除正文数量及失败记录。

## 9. App 使用边界

`experience_evidence` 仍是内部证据，不直接显示为 App 回答。App 只能检索满足以下条件的 `experience_signal_aggregates`：

- 聚合已经审核并发布；
- 关联证据均为有效状态；
- 样本数、来源数和置信度达到配置门槛；
- 数据尚未过期；
- 学校、专业和维度与用户问题匹配。

体验语料只用于归纳长期体验，不覆盖学校官网、教育部门等 S1/S2 官方事实。样本不足时 App 使用正常引导语言，不显示“清洗、入库、同步失败”等后台术语。

## 10. 失败处理与可恢复性

- Redis 不可用：停止接收新的 B 类正文，不降级为把所有原文直接写 MySQL。
- AI 超时：临时正文保留到 TTL，任务进入可重试状态，不进入人工审核列表伪装成待审。
- 数据库写入失败：有效证据使用幂等键重试，不能重复入库。
- 拒绝正文清理失败：记录清理失败事件并告警，后台重试，不能显示为已删除。
- 来源权限失效：暂停对应平台，已通过历史证据按时效和权限策略决定是否继续参与聚合。
- 处理规则升级：记录规则版本；需要重算时从仍在保留期内的脱敏候选重跑，不恢复已删除的垃圾正文。

## 11. 测试与验收

### 11.1 自动测试

- 明确垃圾在调用 AI 前被拒绝，MySQL 中不存在其正文；
- 自动拒绝后 Redis 只保留带 TTL 的不可逆哈希；
- 自动通过必须同时满足质量、信息价值、可信度、风险和来源权限条件；
- `requiresHumanReview=true` 的高分内容仍进入候选表；
- 负面但具体、可信的内容不会因为情绪被自动拒绝；
- 人工通过会原子地创建有效证据并清理候选正文；
- 人工拒绝会清理正文并保留最小审计信息；
- 待审、拒绝和未发布内容无法被 App 检索；
- 重复运行不会重复创建有效证据；
- Redis、AI、数据库和来源受阻路径均有可恢复状态与监控计数。

### 11.2 北京大学首轮验收

- 有效证据至少 500 条，目标 800 条；
- 七个维度均有有效数据，并显示目标缺口；
- 人工审核量不超过原始采集量的 3%；
- 随机抽检自动通过样本，记录准确率和主要误判类型；
- 自动淘汰正文不出现在 MySQL 内容字段中；
- 管理端可以从批次计数追踪到有效证据和已发布聚合；
- App 只能命中已发布聚合，并能正确回答北京大学对应维度的问题。

## 12. 实施边界与顺序

本次实现只调整 B 类体验语料链路及现有内容监控中心，不修改邀请码、用户管理或其他无关页面。

建议实施顺序：

1. 增加候选表、拒绝审计字段和迁移脚本；
2. 将临时正文前移到 Redis，并补齐主动清理；
3. 调整规则清洗、AI 分流和自动审核策略；
4. 改造人工审核接口与管理端展示；
5. 增加配额编排、补采和人工审核率监控；
6. 安全迁移现有待审与拒绝数据；
7. 运行北京大学 500–800 条有效证据验收；
8. 首轮质量稳定后，再分别设计并接入新平台适配器。
